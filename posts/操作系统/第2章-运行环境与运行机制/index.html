一、 核心思想：异常控制流#

异常控制流是理解操作系统一切交互和机制的关键。

  • 理解ECF，就可以理解：
    1. 应用程序与操作系统的交互。
    2. 并发。
    3. 软件异常的工作原理。
  • 操作系统是由“中断/异常/事件驱动”的：操作系统本身是一个被动的管理程序，通过响应来自硬件（中断）和软件（异常）的各种事件来获得CPU控制权并开展工作。

二、 运行环境（硬件基础）#

操作系统运行需要硬件提供以下支持：

1. 中央处理器#

  • 两类寄存器：
    • 用户可见寄存器：数据、地址、条件码寄存器。
    • 控制和状态寄存器：用于控制处理器。
      • 程序计数器：下一条指令地址。
      • 程序状态字：包含条件码和系统状态位（如中断允许位）。
  • 处理器状态/模式：
    • 用户态：运行用户程序，不能执行特权指令。
    • 内核态：运行操作系统程序，可以执行一切指令。
    • 模式转换：
      • 用户态 → 内核态：唯一途径是通过中断/异常/陷入。
      • 内核态 → 用户态：通过设置PSW。
  • 特权指令：只能在内核态下由操作系统使用的指令。

2. 中断与异常机制#

这是操作系统的“引擎”，是ECF的具体实现。

  • 中断：来自CPU外部（如I/O设备、时钟），异步发生。总是返回到下一条指令。

  • 异常：来自CPU内部（执行指令时），同步发生。

    • 陷入：有意识安排的，如系统调用。返回到下一条指令。
    • 故障：可恢复的错误，如页故障。可能返回到当前指令重新执行。
    • 终止：不可恢复的错误，不会返回。

  • 中断/异常处理流程（软硬协同）：

    • 硬件负责（响应）：
      1. 检测中断/异常。
      2. 保存部分现场（PC、PSW）。
      3. 关中断（针对中断门）。
      4. 通过中断向量号查询中断描述符表，找到处理程序入口地址。
    • 软件负责（处理）：
      1. 保存完整现场（所有寄存器）。
      2. 分析具体原因并执行处理程序。
      3. 恢复现场。
      4. 执行返回指令（如IRET），回到用户程序。

  • 关键数据结构：

    • 中断描述符表：存储中断门/陷阱门描述符，包含处理程序的段选择符和偏移量。IDTR寄存器指向它。
    • 系统调用是通过陷入指令（如int 0x80）触发的一个异常。

三、 运行机制（系统调用）#

系统调用是用户程序主动与操作系统交互的唯一接口。

1. 系统调用机制设计#

  1. 陷入指令：引发异常，完成用户态到内核态的切换（如int 0x80, syscall）。
  2. 系统调用号：每个系统功能一个唯一编号，存放在EAX寄存器。
  3. 系统调用表：存储系统调用服务例程的入口地址，根据调用号索引。
  4. 参数传递：通过寄存器（如EBX, ECX, EDX）或内存堆栈。

2. 系统调用执行流程（以Linux x86的write为例）#

  1. 用户态：应用程序调用C库函数write()。
  2. 封装例程：C库将系统调用号(4)放入EAX，参数放入相应寄存器，执行int 0x80。
  3. 硬件响应：
    • 切换栈（用户栈→内核栈）。
    • 保存现场（用户态SS:ESP, EFLAGS, CS:EIP）。
    • 通过IDT[128]找到system_call入口。
  4. 内核态：
    • system_call保存所有寄存器(SAVE_ALL)。
    • 根据EAX中的调用号，查sys_call_table，调用sys_write()。
    • sys_write()执行具体操作。
  5. 返回：
    • 返回值存入EAX。
    • 跳转到ret_from_sys_call，可能进行调度、信号处理。
    • RESTORE_ALL恢复现场，执行IRET返回用户态。

3. 重要区别#

  • 系统调用 vs 函数调用：
特征 系统调用 函数调用
执行环境 内核态 用户态
切换方式 陷入指令 + 软硬件上下文切换 CALL / RET 指令
性能开销 大 小
  • 系统调用 vs C库函数 vs API：
    • API：是一个函数定义，说明如何获得一个给定的服务。
    • C库函数：是API的一种实现，可能完全在用户态，也可能封装了系统调用。
    • 系统调用：是操作系统内核实现的真正服务例程。

四、 机制与策略分离#

  • 机制：提供怎么做的能力（如：系统调用机制、中断处理机制）。—— 操作系统实现
  • 策略：决定做什么、何时做（如：调度算法、页面置换算法）。—— 可由用户或上层软件决定

操作系统设计应尽可能将机制与策略分离，以提高灵活性和可扩展性。

五、事件类别#

中断 - 来自CPU外部，异步#

中断主要由硬件设备产生，通常与当前执行的指令没有直接关系。

1. I/O 中断#

由各种输入/输出设备产生，表示一个I/O操作已经完成或设备需要关注。

  • 磁盘中断：当磁盘读写操作完成时，磁盘控制器会发出中断，通知CPU数据已准备好或已写入。
  • 网络中断：网卡接收到新的数据包，或数据包发送完成时产生。
  • 键盘/鼠标中断：用户按下按键或移动鼠标时产生，将输入事件通知给系统。
  • 声卡中断：处理音频流的输入或输出。
  • USB设备中断：各种USB设备（如U盘、摄像头）与系统通信时产生。
2. 时钟中断#

由系统的定时器硬件周期性产生，与具体的I/O设备无关，是操作系统心跳的来源。

  • 系统时钟中断：以固定频率（如100Hz或1000Hz）发生，是操作系统实现时间片轮转调度、更新系统时间、计算进程执行时间的基础。
  • 高精度事件定时器：为需要更精确时间管理的应用提供支持。
3. 硬件故障#

通常指非预期的、严重的硬件问题，虽然罕见，但一旦发生通常难以恢复。

  • 内存校验错误：例如ECC内存检测到无法纠正的错误。
  • 电源故障：系统检测到电源异常。
  • 总线错误：在访问内存或设备时，在系统总线上检测到物理错误。

异常 - 来自CPU内部，同步#

异常是由当前正在执行的指令直接触发的。

1. 陷入#

这是有意识、故意安排的异常，通常用于实现从用户态到内核态的切换。

  • 系统调用：这是最典型的陷入。用户程序通过执行一条特殊指令（如 x86 的 int 0x80/syscall，RISC-V 的 ecall）来主动请求操作系统提供服务。
  • 断点指令：由调试器故意插入到被调试程序中的指令（如 x86 的 int 3），用于暂停程序执行，进入调试状态。
  • 调试单步：通过设置标志位，让CPU每执行一条指令就产生一次异常，方便调试。
2. 故障#

这是由指令执行过程中遇到的可恢复的错误 触发的。处理程序会修复这个错误，然后重新执行这条指令。

  • 页错误：这是最常见、最重要的故障。
    • 缺页：要访问的页面不在物理内存中。处理程序会从磁盘调入该页，然后重新执行指令。
    • 写保护错误：试图向只读的页面写入数据。
    • 权限错误：用户程序试图访问内核空间的页面。
  • 除零错误：执行除法指令时除数为零。
  • 浮点异常：如浮点溢出、下溢等。
3. 终止#

这是由不可恢复的严重硬件错误 导致的，处理程序通常无法修复，只能终止出错的进程甚至导致系统崩溃。

  • 机器检查：检测到致命的硬件问题，如CPU温度过高、严重的硬件损坏。
  • 奇偶校验错误：在关键系统总线上检测到数据损坏且无法恢复。
  • 双重故障：在尝试处理一个异常时，又发生了另一个异常。
总结表格#
类别 原因 异步/同步 返回行为 详细举例
中断 来自I/O设备、其他硬件部件 异步 总是返回到下一条指令 磁盘中断、网络中断、键盘中断、时钟中断、硬件故障中断
陷入 有意识安排的 同步 返回到下一条指令 系统调用、断点调试、单步调试

终止 不可恢复的错误 同步 不会返回 硬件故障、机器检查、双重故障

六、一些问题#

1. 应用程序是如何与操作系统交互的？#

  • 通过系统调用（System Call），这是操作系统提供给编程人员的唯一接口。应用程序通过执行特殊的陷入指令（如 int 0x80、syscall）触发异常，从而从用户态切换到内核态，由操作系统内核代为执行请求的服务。

2. 怎样理解“操作系统是由中断/异常/事件驱动的”？#

  • 操作系统本身通常不主动执行，而是被动响应来自硬件（如I/O设备中断、时钟中断）或软件（如系统调用、页故障）的事件。这些事件改变了CPU的控制流，使操作系统获得控制权并执行相应处理程序。

3. 中断/异常的来源有什么不同？处理方式是一样的吗？#

  • 中断：来自外部硬件设备，异步发生（如I/O完成）。
  • 异常：由CPU执行指令时同步触发（如除零、页故障、陷入指令）。
  • 处理方式：硬件响应流程类似（通过中断向量表/IDT转移控制权），但软件处理程序根据具体类型不同。

4. 回顾一下：ICS对异常的描述及分类#

  • 异常被分类为：
    • 陷入（Trap）：有意安排的（如系统调用），返回到下一条指令。
    • 故障（Fault）：可恢复的错误（如页故障），可能重新执行当前指令。
    • 终止（Abort）：不可恢复的错误，不会返回。

5. 中断/异常处理流程中，哪些工作是硬件负责的？哪些是软件负责的？#

  • 硬件：检测中断/异常、保存部分现场（如PC、PSW）、关中断（部分情况）、通过中断向量表定位处理程序入口。
  • 软件：保存完整现场、分析原因、执行处理功能、恢复现场、返回。

6. 从中断响应到中断处理程序执行结束，计算机系统经过了哪些流程？#

  • 硬件检测中断 → 保存现场 → 查中断向量表 → 转至处理程序 → 软件保存现场 → 执行处理 → 恢复现场 → 返回被中断程序。

7. 操作系统初始化与中断/异常有哪些关联？#

  • 操作系统在初始化阶段会设置中断描述符表（IDT） 和系统调用表，为每个中断/异常向量指定相应的处理程序入口地址。

8. 什么是软件异常？它是如何工作的？#

  • “理解ECF就可以理解软件异常如何工作”。软件异常通常指由程序主动触发的异常（如系统调用），通过执行陷入指令实现，引发CPU异常控制流转移至内核处理程序。

9. X86有哪些控制和状态寄存器？所起的作用是什么？#

  • 程序计数器（PC/EIP）：下一条指令地址。
  • 程序状态字（PSW/EFLAGS）：条件码、系统标志（如IF中断允许位）。
  • 控制寄存器：如CR0-CR4，控制CPU操作模式（如分页、保护模式）。
  • 段寄存器：CS、DS、ES、SS等，用于内存分段管理。

10. X86在Pentium II 300之后提供了SYSENTER/SYSEXIT指令，为什么？与INT 0x80/IRET有什么不同？X86-64提供的系统调用指令是什么？#

  • 原因：SYSENTER/SYSEXIT 提供了更快速的系统调用进入/返回机制，减少了传统 int 0x80/iret 的硬件开销。
  • 不同：SYSENTER/SYSEXIT 不经过中断描述符表（IDT），直接切换到预设的内核栈和代码段，性能更高。
  • x86-64系统调用指令：syscall / sysret。

11. 关于基于X86体系结构的Linux的系统调用实现：#

  • （1）系统调用入口程序system_call()与中断描述符表是什么关系？与系统调用表是什么关系？

    • 与IDT关系：IDT中第128项（0x80）指向 system_call 作为总入口。
    • 与系统调用表关系：system_call 根据EAX中的系统调用号，查系统调用表（sys_call_table）跳转到具体的内核处理函数（如 sys_write）。

  • （2）系统调用处理结束后，处理器转去执行哪个模块？

    • 执行 ret_from_sys_call 例程，进行进程调度、信号处理等后续工作，最后恢复现场返回用户态。

12. 系统调用与函数/过程调用的区别是什么？系统调用与C函数调用的区别？系统调用与API的关系？#

  • 系统调用 vs 函数调用：
    • 系统调用涉及特权级切换（用户态→内核态），使用陷入指令，由操作系统内核执行。
    • 函数调用在同一特权级下执行，使用CALL/RET指令。
  • 系统调用 vs C函数调用：C库函数（如 printf）可能封装系统调用（如 write），但并非所有C函数都触发系统调用。
  • 系统调用 vs API：API是编程接口，系统调用是底层实现。API函数可能通过系统调用实现，也可能完全在用户态完成。
