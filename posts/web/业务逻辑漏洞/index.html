对客户端控制的过度信任#

一个根本错误的假设是用户只会通过提供的网页界面与应用交互。这尤其危险，因为它进一步假设客户端验证能防止用户提供恶意输入。

例如，在装入购物车的页面抓包，将货品价格从1337$ 改为0.01$，就能够支付成功。

无法处理非常规输入#

应用逻辑的一个目标是限制用户输入到符合业务规则的值。比如，数字数据类型可能接受负值。根据相关功能，业务逻辑可能不允许这样做。然而，如果应用程序未能进行足够的服务器端验证并拒绝该输入，攻击者可能能够传递负值，从而引发不想要的行为。

高级逻辑漏洞#

例如，在装入购物车的页面，发现没有 price 参数，只有 quantity 参数。把 quantity 参数改为负，结果金额不能为负。于是，再凑几件其他商品，控制金额就行。

低级逻辑缺陷#

例如，在装入购物车的页面，quantity 参数不能改为负数了。在 intruder 模块中爆破，发现一次最多放入的数量限制为99。再把quantity 参数设置为99$$，选择 Null payloads模式进行爆破。也就是不断添加99个数量。刷新页面，发现金额会在一定数量上变为负数。这是因为金额可能是用32位的 int ( -2,147,483,648 ~ 2,147,483,647)定义的。一旦金额值超过最大值，就会变为负数。于是，利用这一点，搭配其他商品，让总金额小于100而大于0即可。

特殊输入不一致#

例如，在一个绑定邮件地址的登录程序。先在主页面刷新，在Burp中找到 Target->Engagement Tools->Discover Content，点击 Session is not running，然后转到 Site map 模块就能看到有 /admin 这个网址。这个步骤就相当于智能化的dirsearch工具。进入 /admin，发现需要以DontWannaCry用户的身份进行登录。于是，注册一个账户，邮件地址就是给出的 attacker@exploit-EMAILID.exploit-server.net，在其中会收到确认链接。然后发现这个账户是没有用的，因为在注册页面就提示，管理员账户是 @dontwannacry.com。可是，我们并没有这样的邮箱，也就是收不到链接。只能考虑截断。注册时的邮件地址限制为255个字符，我们就让 anything@dontwannacry.com 刚好是255个字符，后面拼接已有的邮件地址 .exploit-EMAILID.exploit-server.net。这样就能够注册并登录成功。

对用户行为做出错误假设#

可信用户并不总是值得信赖#

应用程序看似安全，是因为它们实施了看似强有力的执行业务规则的措施。不幸的是，一些应用程序犯了一个错误，认为通过这些严格控制后，用户及其数据可以被无限期地信任。这可能导致从那时起对相同管控的执行相对宽松。

例如，如上的绑定邮件地址的登录程序。在常规登录页面，会提示管理员的邮件地址是 @dontwannacry.com。于是，常规登录，把邮件地址修改即可。

并不总是提供强制输入#

一个误解是用户总是会为强制输入字段提供值。浏览器可能会阻止普通用户在没有必要输入的情况下提交表单，但正如我们所知，攻击者可以在传输过程中篡改参数。这甚至延伸到完全移除参数。这适用于URL和参数 POST，但别忘了检查Cookie。

例如，以普通用户的身份登录之后，要更改密码以用管理员身份登录。但是，在程序中，更改密码需要原密码，而我们并不知道管理员的密码。在测试过程中，发现原密码这个参数可以直接删除。于是，更改管理员的密码成功。

不遵循预期的顺序#

许多事务依赖于由一系列步骤组成的预定义工作流程。网页界面通常会引导用户完成这一流程，每次完成当前流程时都会引导他们进入下一步。然而，攻击者不一定会遵循这个预定的顺序。忽视这种可能性可能导致危险的缺陷，而这些缺陷相对容易被利用。

例如，在购物时，先下单一件小商品，发现有一个确认页面 /cart/order-confirmation?order-confirmed=true。这个页面中并没有对购物车中的商品进行确认，也没有考虑余额是否足够。于是，把目标商品放入购物车之后，重放这个页面即可。

再例如，登录的时候，会有两个页面：一个是正常的 POST /login 页面，另一个是选择角色的 GET /role-selector 页面。将后者丢弃，直接改为 /admin 页面，默认为管理员角色。

领域特定的缺陷#

网店的折扣功能是寻找逻辑缺陷时的经典攻击面。这对攻击者来说可能是个宝藏，因为折扣的应用存在各种基本逻辑缺陷。比如，考虑一家网店对超过1000美元的订单提供10%折扣。如果业务逻辑未能检查折扣应用后订单是否被更改，这种机制可能容易被滥用。在这种情况下，攻击者可以将商品加入购物车，直到达到1000美元门槛，然后在下单前移除不想要的物品。即使订单不再符合预期标准，他们也会获得折扣。

例如，在折扣页面，发现新登录的用户可以获得优惠券，主页下面还有对注册新闻订阅的优惠券。两种优惠券不断交替使用，足够把金额压缩。

再例如，还是折扣的场景。如果用优惠券购买10美元的卡，只需花费7美元，而且兑换的礼物积分让整体余额增加到了103美元。也就是说，这套流程就是让余额增加的。那重复这套流程就行了。涉及到多个页面，可以选择用Burp intruder自动执行。首先确认需要的页面，有购物车页面（含有需要购买的卡） POST /card，提交优惠券页面 POST /cart/coupon，审查中转 POST /cart/checkout，提交订单并显示积分码 GET /cart/order-confirmation?order-confirmed=true，兑换积分 POST /gift-card，最后跳转到的账户页面 GET /my-account。然后添加一个宏进行自动执行。Project options->Sessions->add。Scope选项卡下，URL Scope->Include all URLs。Details 选项卡下，Run actions->add->Run a macro->Select macro->add，然后将上面的需要页面（除掉最后一个）都添加进去并确定。在已选的列表中，点击 GET /cart/order-confirmation?order-confirmed=true，Configure item->add，命名好参数（比如命名为 gift-card）并选中响应的积分码，确定；点击 POST /gift-card，Configure item->Parameter handling，把 gift-card 参数改为从先前的响应派生。接着可以测试一下宏是否成功。最后，把 GET /my-account 发送给 intruder，空转，注意需要自动执行的次数，并将资源池设置为1。解决。
