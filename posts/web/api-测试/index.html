API测试非常重要，因为API中的漏洞可能破坏网站的机密性、完整性和可用性的核心方面。本节重点关注 RESTful 和 JSON API。

API 侦察#

要开始 API 测试，首先需要尽可能多地了解该 API 的信息，以发现其攻击面。一旦确定了端点，需要确定如何与它们交互。这使得能够构建有效的HTTP请求来测试API。例如，应该了解以下信息：

  • API处理的输入数据，包括强制和可选参数。
  • API 接受的请求类型，包括支持的 HTTP 方法和媒体格式。
  • 速率限制和认证机制。

API 文档#

API 通常会被文档化，以便开发者知道如何使用和集成它们。文档既可以是人类可读的形式，也可以是机器可读的形式。设计的可读文档旨在帮助开发者理解如何使用 API。它可能包含详细的解释、示例和使用场景。机器可读文档设计为由软件处理，用于自动化API集成和验证等任务。它采用了像JSON或XML这样的结构化格式。

发现API文档#

即使API文档没有公开，仍然可以通过浏览使用该API的应用程序访问它。如果确定了某个资源的端点，务必调查基础路径。比如，如果确定了资源端点 /api/swagger/v1/users/123，那么应调查以下路径：

  • /api/swagger/v1
  • /api/swagger
  • /api

例如，在电子邮件页面更新邮件之后，发现有一个名为 /api/user/... 的页面。经过测试，/api 是有效的API文档。那就进入并点击 DELETE 行，删除目标用户。

识别API端点#

浏览应用时，寻找提示 URL 结构中 API 端点的模式，例如 /api/。还要注意JavaScript文件。这些节点可能包含未通过浏览器直接触发的API端点引用。

识别支持的HTTP方法#

HTTP 方法指定对资源执行的操作。例如：

  • GET- 从资源中检索数据
  • PATCH- 对资源进行部分更改
  • OPTIONS- 检索可用于资源的请求方法类型信息

API端点可能支持不同的HTTP方法。因此，在研究API端点时，测试所有可能的方法非常重要。这可能帮助识别更多端点功能，从而打开更多攻击面。例如，端点 /api/tasks 可能支持以下方法：

  • GET /api/tasks- 检索任务列表
  • POST /api/tasks- 创建新任务
  • DELETE /api/tasks/1- 删除任务

识别支持的内容类型#

API端点通常期望数据格式特定。因此，它们的行为可能会根据请求中提供的数据内容类型而有所不同。更改内容类型可能导致：

  • 触发错误，揭示有用信息。
  • 绕过有缺陷的防御。
  • 利用处理逻辑的差异。例如，一个 API 在处理 JSON 数据时可能安全，但在处理 XML 时容易受到注入攻击。

要更改内容类型，先修改 Content-Type 头部，然后相应地重新格式化请求体。

例如，要用无余额的账户购买一件商品。进入商品的API端点，把 GET 请求改为 POST 请求。但有提示请求类型只允许 GET 和 PATCH。于是，将请求类型改为 PATCH。又提示 Content-Type 类型错误，于是添加 Content-Type: application/json。再提示内部服务器错误，那就添加一个空json。最后经过参数的提示，添加的内容是：

1{'price':0}

这样就可以零元购。

寻找隐藏参数#

大规模分配漏洞#

批量赋值（也称为自动绑定）可能无意中创建隐藏参数。它发生在软件框架自动将请求参数绑定到内部对象的字段时。因此，批量赋值可能导致应用程序支持开发者从未打算处理的参数。

识别隐藏参数#

由于批量赋值是从对象字段创建参数，通常可以通过手动检查API返回的对象来识别这些隐藏参数。比如，考虑一个 PATCH /api/users/ 请求，允许用户更新用户名和邮箱，包含以下 JSON：

1{
2    "username": "wiener",
3    "email": "wiener@example.com",
4}

一个并发的 GET /api/users/123 请求返回以下 JSON:

1{
2    "id": 123,
3    "name": "John Doe",
4    "email": "john@example.com",
5    "isAdmin": "false"
6}

这可能表明隐藏的 id 和 isAdmin 参数与内部用户对象绑定，以及更新后的用户名和电子邮件参数。

测试大规模分配漏洞#

要测试是否可以修改枚举的 isAdmin 参数值，将其添加到 PATCH 请求中：

1{
2    "username": "wiener",
3    "email": "wiener@example.com",
4    "isAdmin": false,
5}

此外，发送一个带有无效 isAdmin 参数值的 PATCH 请求：

1{
2    "username": "wiener",
3    "email": "wiener@example.com",
4    "isAdmin": "foo",
5}

如果应用表现不同，这可能表明无效值影响了查询逻辑，但有效值没有影响。这可能表明该参数可以被用户成功更新。然后，可以发送一个 PATCH 请求，并将 isAdmin 参数值设置为 true，以尝试利用该漏洞：

1{
2    "username": "wiener",
3    "email": "wiener@example.com",
4    "isAdmin": true,
5}

例如，购买商品后，发现有两个API端点 /api/。第一个是 GET 请求，返回一个 json。第二个是POST 请求，包含一个 json。但是，两个 json的具体内容不同。于是，将 GET 的 json复制到 POST 中，并修改折扣为100，通过。

服务器端参数污染#

服务器端参数污染是指网站在服务器端请求中嵌入用户输入，指向内部 API，且没有充分编码。这意味着攻击者可能能够操控或注入参数，从而使他们能够实现以下行为：

  • 覆盖现有参数。
  • 修改应用行为。
  • 访问未经授权的数据。

查询参数、表单字段、头部和 URL 路径参数都可能存在该漏洞。

查询字符串测试#

要测试查询字符串中的服务器端参数污染，请在输入中放置查询语法字符，如 #、& 和 =，并观察应用程序的响应。考虑一个漏洞应用，允许根据用户名搜索其他用户。当搜索用户时，浏览器会发出以下请求：

1GET /userSearch?name=peter&back=/home

为了获取用户信息，服务器会通过以下请求查询内部 API：

1GET /users/search?name=peter&publicProfile=true

截断查询字符串#

可以使用 URL 编码的 # 字符来尝试截断服务器端的请求。为了帮助解释响应，还可以在 # 字符后添加一个字符串。比如，可以修改查询字符串为以下内容：

1GET /userSearch?name=peter%23foo&back=/home

前端将尝试访问以下URL：

1GET /users/search?name=peter#foo&publicProfile=true

检查响应中是否有关于查询是否被截断的线索。例如，如果响应返回用户 peter，服务器端的查询可能已被截断。如果返回 Invalid name 错误信息，应用程序可能将 foo 视为用户名的一部分。这表明服务器端的请求可能没有被截断。

如果能够截断服务器端请求，这将取消将 publicProfile 字段设置为 true 的要求。可能能够利用这一点返回非公开的用户资料。

注入无效参数#

可以使用带有 URL 编码的&字符尝试在服务器端请求中添加第二个参数。比如，可以修改查询字符串为以下内容：

1GET /userSearch?name=peter%26foo=xyz&back=/home

这导致服务器端向内部API发出以下请求：

1GET /users/search?name=peter&foo=xyz&publicProfile=true

查看回复，了解额外参数是如何解析的。例如，如果响应未变，这可能表明该参数已成功注入但应用忽略了该参数。

注入有效参数#

如果能修改查询字符串，就可以尝试给服务器端请求添加第二个有效参数。比如，如果已经确定了参数 email，可以将其添加到查询字符串中，具体如下：

1GET /userSearch?name=peter%26email=foo&back=/home

这导致服务器端向内部API发出以下请求：

1GET /users/search?name=peter&email=foo&publicProfile=true

查看回复，了解额外参数是如何解析的。

覆盖现有参数#

为了确认应用是否易受服务器端参数污染影响，可以尝试覆盖原始参数。通过注入同名的第二个参数来实现这一点。比如，可以修改查询字符串为以下内容：

1GET /userSearch?name=peter%26name=carlos&back=/home

这导致服务器端向内部API发出以下请求：

1GET /users/search?name=peter&name=carlos&publicProfile=true

内部 API 解析两个 name 参数。这取决于应用程序如何处理第二个参数，影响会有所不同。这在不同的网络技术中有所差异。比如：

  • PHP 只解析最后一个参数。这将导致用户搜索 carlos
  • ASP.NET 会将两个参数合并。这将导致用户搜索peter,carlos，可能会出现Invalid username 的错误信息
  • Node.js / express 只解析第一个参数。这将导致用户搜索 peter，结果保持不变

如果能够覆盖原始参数，可能能够进行利用。比如，可以在请求中添加 name=administrator。这能够以管理员用户身份登录。

例如，要以 administrator 的身份去删除一个账户，那先点击“忘记密码”。虽然没有邮箱，但是可以分析页面 POST /forgot-password。在提交的内容后面添加编码后的 # 和 & 字符进行测试。发现 &filed= 可用。那就用Burp自带的 Server-side variable names 表进行爆破。用爆破得到的值 email 填充，发现效果和没有field参数时的效果一样。那去查看调用的页面forgotPassword.js，发现发现会去url中拿 reset-token 这个参数，并填入到GET请求中。那将 field 参数赋值为 reset_token，响应里给出了reset_token的真实值。那据此构造GET请求，就能顺利更改密码。

测试 REST 路径#

RESTful API 可能会将参数名和值置于 URL 路径中，而非查询字符串。例如，考虑路径/api/users/123，URL 路径可以分解如下：

  • /api是根API端点
  • /users表示一种资源，在此例中为 users
  • /123表示一个参数，这里是特定用户的标识符

考虑一个应用程序，允许根据用户名编辑用户资料。请求发送到以下端点：

GET /edit_profile.php?name=peter

这导致了以下服务器端请求：

GET /api/private/users/peter

攻击者可能能够操控服务器端的 URL 路径参数来利用该 API。可以将 URL 编码的 peter/../admin 提交为 name 参数的值：

GET /edit_profile.php?name=peter%2f..%2fadmin

这可能导致以下服务器端请求：

GET /api/private/users/peter/../admin

如果服务器端客户端或后端API对该路径进行规范化，则可能解析为/api/private/users/admin

例如，与上面类似的场景，但只是在&字符时提示有参数被截断。那将username参数值改为./administrator，发现正常显示，也就是解析了路径遍历。于是，采用路径遍历，发现5个../就移动到了api根路径之外。那就读取配置文件../../../../openapi.json，找到一个可用的api：

1api/internal/v1/users/{username}/field/{field}

根据回显，username参数构造为administrator/field/email%23。然后出现了与上一题类似的场景：回显和之前一样。阅读forgotPassword.js文件，将email值改为参数passwordResetToken。但响应又提示不支持这个版本的API，那就用完整的api加上路径遍历：

1&username=../../../../api/internal/v1/users/administrator/field/passwordResetToken%23

从而得到passwordResetToken的值。最后，按照forgotPassword.js文件中构造的路径，成功更改新密码。

结构化数据格式#

攻击者可能能够操控参数，利用服务器处理其他结构化数据格式（如 JSON 或 XML）时的漏洞。为了测试这一点，可以向用户输入注入意想不到的结构化数据，看看服务器的响应。考虑一个应用程序，允许用户编辑个人资料，然后通过服务器端API请求应用更改。当编辑姓名时，浏览器会发出以下请求：

1POST /myaccount name=peter

这导致了以下服务器端请求：

1PATCH /users/7312/update {"name":"peter"}

可以尝试将参数access_level添加到请求中，具体如下：

1POST /myaccount name=peter","access_level":"administrator

如果用户输入未经充分验证或净化就添加到服务器端 JSON 数据中，会导致以下服务器端请求：

1PATCH /users/7312/update {name="peter","access_level":"administrator"}

这可能导致用户peter获得管理员权限。
