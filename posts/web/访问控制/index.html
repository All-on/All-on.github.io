基本概念#

垂直访问控制#

垂直访问控制是一种限制特定类型用户访问敏感功能的机制。通过垂直访问控制，不同类型的用户可以访问不同的应用功能。例如，管理员可能能够修改或删除任何用户的账户，而普通用户则无法访问这些操作。

水平访问控制#

水平访问控制是一种限制特定用户访问资源的机制。通过水平访问控制，不同用户可以访问同类型资源的子集。例如，银行应用允许用户查看自己的账户交易和付款，但不能查看其他用户的账户。

上下文相关访问控制#

上下文依赖访问控制根据应用状态或用户与其交互来限制对功能和资源的访问。上下文相关的访问控制防止用户按错误顺序执行操作。例如，零售网站可能阻止用户在付款后修改购物车内容。

垂直权限升级#

如果用户能够访问他们不被允许访问的功能，这就是垂直特权升级。例如，如果非管理员用户能够访问管理员页面并删除用户账户，这就是垂直权益升级。

未受保护的管理功能#

最基本的垂直权限升级是指应用程序不强制保护敏感功能时。例如，管理功能可能从管理员的欢迎页面链接，但不链接用户的欢迎页面。不过，用户可能可以通过浏览到相关的管理员 URL 访问管理功能。例如，一个网站可能托管在以下URL的敏感功能：

https://insecure-website.com/admin

这可能对任何用户开放，而不仅仅是管理员用户，他们在用户界面中链接到了该功能。在某些情况下，管理网址可能会在其他地方被披露，例如文件 robots.txt ：

https://insecure-website.com/robots.txt

但在某些情况下，敏感功能会通过赋予更难预测的网址来隐藏。这就是所谓“隐蔽性安全”的一个例子。然而，隐藏敏感功能并不能提供有效的访问控制，因为用户可能会通过多种方式发现被混淆的URL。假如一个托管管理功能的应用程序，URL如下：

https://insecure-website.com/administrator-panel-yb556

这个很难猜到。但URL可能在JavaScript中披露。查看源代码即可。

基于参数的访问控制方法#

一些应用程序在登录时确定用户的访问权限或角色，并将这些信息存储在用户可控制的位置。这可能是：

  • 一个隐藏的领域。
  • 一个cookie。
  • 一个预设的查询字符串参数。

例如，在cookie中发现有 admin 参数，只有当为 true 的时候才能以管理员身份操作账户。于是，接下来的每一步都通过抓包修改。

再例如，题目提示到需要参数 roleid 等于2时，才能获得admin权限。终于，在更改电子邮件的页面，看到了响应的 json 中有 roleid=1 。那怎么改呢？在请求的页面的 json 格式中，添加 roleid=2 即可。

平台配置错误导致的访问控制失效#

一些应用程序在平台层执行访问控制。他们通过根据用户角色限制对特定 URL 和 HTTP 方法的访问来实现这一点。例如，应用程序可能配置规则如下：

DENY: POST, /admin/deleteUser, managers

此规则拒绝管理组用户对 URL /admin/deleteUser 上的 POST 方法的访问。在这种情况下，各种问题可能会导致访问控制绕过。一些应用程序框架支持各种非标准的 HTTP 头，可以用来覆盖原始请求中的 URL，例如 X-Original-URL 和 X-Rewrite-URL。如果一个网站使用严格的前端控制来根据 URL 限制访问，但应用程序允许通过请求头覆盖 URL，那么可能可以通过如下请求绕过访问控制：

1POST / HTTP/1.1
2X-Original-URL: /admin/deleteUser
3...

另一种攻击与请求中使用的 HTTP 方法有关。前面描述的前端控制是基于 URL 和 HTTP 方法来限制访问的。一些网站在执行操作时会容忍不同的 HTTP 请求方法。如果攻击者可以使用 GET（或其他）方法对受限 URL 执行动作，他们就可以绕过在平台层实现的访问控制。

例如，如果能够抓住管理员对一个用户升级的页面，并把账户名改为自己。然后将自己的cookie复制上去，将 POST 方法改为 GET ，就能够通过。

URL匹配不一致导致的访问控制失效#

这里有3种情况。一个是，网站在匹配输入请求路径到特定端点的严格程度上各不相同。比如，大小写绕过。

第二个是，如果使用 Spring 框架的开发人员启用了 useSuffixPatternMatch 选项，也可能出现类似的差异。该选项允许将具有任意文件扩展名的路径映射到没有文件扩展名的等效端点。换句话说，对 /admin/deleteUser.anything 的请求仍然会匹配 /admin/deleteUser 模式。在 Spring 5.3 之前，该选项默认是启用的。

第三个是，在后端添加一个反斜杠 / 绕过。比如，可能会遇到 /admin/deleteUser 和 /admin/deleteUser/ 是否被视为不同端点的差异。

水平权限升级#

水平权限升级攻击可能使用与垂直权限升级类似的利用方法。

更改id#

用户可能使用以下URL访问自己的账户页面：

https://insecure-website.com/myaccount?id=123

如果攻击者将参数值修改为另一用户的id，他们可能会访问另一用户的账户页面，以及相关的数据和函数。

某些情况下，应用程序会检测用户未被允许访问资源，并返回登录页面重定向。然而，包含重定向的响应可能仍包含目标用户的一些敏感数据，因此攻击仍然成功。

id不可预测#

在某些应用中，可利用参数没有可预测的值。例如，应用程序可能使用全局唯一标识符（GUID）来识别用户，而不是递增数字。这可能防止攻击者猜测或预测其他用户的标识符。然而，属于其他用户的 GUID 可能会在应用中被引用用户的其他地方披露，如用户消息或评论。

例如，找到受害者曾经发表过的一篇博客。点击进入主页。在网页中就能够找到难以预测的 UserId 。然后像上面那样更改即可。

水平到垂直权限升级#

通常，水平权限升级攻击可以通过破坏更高权限用户而转变为垂直权限升级。例如，水平升级可能允许攻击者重置或捕获属于其他用户的密码。如果攻击者针对管理员用户并攻破其账户，则可以获得管理员访问权限，从而进行垂直权力提升。

例如，在自己的页面发现密码是直接泄露的。于是，尝试将账户名改为管理员 administrator 的，这样就能够得到管理员的密码。然后以管理员的身份进行登录。

不安全的直接对象引用#

不安全的直接对象引用（IDOR）是访问控制漏洞的一个子类别。IDOR发生在应用程序使用用户输入直接访问对象，攻击者可能修改输入以获得未授权访问时。常见的有两种。一种是直接引用数据库对象的IDOR漏洞。一个网站，通过从后端数据库获取信息，使用以下URL访问客户账户页面：

https://insecure-website.com/customer_account?customer_number=132355

在这里，客户编号直接作为后端数据库查询中的记录索引使用。如果没有其他控制措施，攻击者可以简单地修改 customer_number 的数值，绕过访问控制查看其他客户的记录。这是一个导致横向权限升级的IDOR漏洞示例。

另一种是直接引用静态文件的IDOR漏洞。IDOR 漏洞通常发生在敏感资源位于服务器端文件系统的静态文件中。例如，一个网站可能会用递增的文件名将聊天消息文字稿保存到磁盘，允许用户通过访问如下URL来获取这些内容：

https://insecure-website.com/static/12144.txt

在这种情况下，攻击者可以简单修改文件名，获取其他用户创建的文字稿，从而可能获取用户凭证和其他敏感数据。

例如，在发送信息时，发现聊天记录位于 2.txt 中。于是，稍加改动，改为 1.txt ，显示出了了密码。

多步流程中的访问控制漏洞#

许多网站通过一系列步骤实现重要功能。这种情况很常见：

  • 需要捕捉各种输入或选项。
  • 用户需要在执行操作前审核并确认细节。

比如，更新用户信息的管理功能可能包括以下步骤：加载包含特定用户详细信息的表单、提交修改、请查看更改并确认。有时，网站会对部分步骤实施严格的访问控制，但忽略其他步骤。想象一个网站，访问控制正确应用于第一步和第二步，但对第三步却没有。网站假设用户只有在完成第一步且受控的第一步时，才能达到第三步。攻击者可以通过跳过前两步，直接提交带有所需参数的第三步请求，从而获得对该函数的未授权访问。

例如，管理员在升级一个账户的时候，分为两步：提权和确定。先抓住这两个页面。然后会发现第一个页面没用。无论是覆盖账户名，还是覆盖cookie，都会提示“未授权”。那么，操作第二个页面，即“确认”页面，成功。

基于 Referer 的访问控制#

一些网站根据 HTTP 请求中提交的 Referer 头来控制访问。浏览器可以在请求中添加 Referer 头，以指示哪个页面发起了请求。

比如，一个应用程序在 /admin 的主管理页面上强制执行了访问控制，但对于诸如 /admin/deleteUser 的子页面，仅检查 Referer 头。如果 Referer 头包含主 /admin URL，则允许该请求。在这种情况下，Referer 头可以被攻击者完全控制。这意味着他们可以通过提供所需的 Referer 头伪造对敏感子页面的直接请求，并获得未经授权的访问。

基于位置的访问控制#

有些网站会根据用户的地理位置来实施访问控制。这可能适用于银行应用或媒体服务，这些地方适用州法律或商业限制。这些访问控制通常可以通过使用网络代理、VPN或操作客户端地理定位机制来绕过。

预防#

通过采取防御深度方法并应用以下原则，可以预防访问控制漏洞：

  • 绝不要仅依赖混淆来控制访问。
  • 除非资源是打算公开访问的，否则默认拒绝访问。
  • 尽可能使用统一的应用范围机制来执行访问控制。
  • 在代码层面，强制开发者声明每个资源允许的访问权限，并默认拒绝访问。
  • 彻底审计和测试访问控制，确保其按设计正常工作。
